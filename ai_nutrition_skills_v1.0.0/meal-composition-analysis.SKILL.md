# Skill: meal-composition-analysis

## Purpose

Convert one or more user-provided meal images and optional text into a
structured, editable meal composition. The output is a hypothesis for
the user to review---not a verified nutrition report.

This Skill must not invent exact weights, ingredients, restaurant
identities, product identities, or nutrient values. It must not query
nutrition sources or generate the final nutrition report.

## Preconditions

-   The app has obtained the user's consent to send the selected image
    to the configured AI provider.
-   The app supplies a unique `meal_id` and the image(s), or an image
    reference the runtime can access.
-   The app may supply optional user text, locale, known context, and
    prior composition data for edits.
-   Do not assume access to the phone's local database. The app owns
    local persistence.

## Inputs

Required: - `meal_id`: stable identifier generated by the app. -
`image_inputs`: at least one image or an accessible image reference.

Optional: - `user_text`: user description,
e.g. "這是烤雞腿，不是炸雞". - `locale`: preferred language; default
`zh-TW`. - `existing_composition`: prior structured output if the user
is editing. - `edit_request`: natural-language change request. -
`known_context`: only user-provided context such as restaurant or
product name.

## Workflow

1.  **Inspect image usability**
    -   Check whether the image contains a visible meal and is
        sufficiently clear.
    -   If no meal is visible, the image is corrupted, or the meal is
        too obscured, return `needs_user_input` with a concise reason.
        Do not guess.
2.  **Identify visible components**
    -   List each visually distinguishable item separately where
        practical (e.g. rice, grilled chicken, leafy vegetables, sauce).
    -   Separate distinct foods rather than collapsing an entire mixed
        plate into one item when components can reasonably be
        distinguished.
    -   For mixed dishes, identify the dish and list visually
        supportable internal ingredients in `ingredients`; place
        plausible but unconfirmed ingredients in `candidate_names`.
    -   Leave `ingredients` empty for a simple food when no internal
        ingredients can be distinguished. Never infer a full recipe
        from the dish name alone.
3.  **Estimate portion cautiously**
    -   For each separately listed food item, actively consider an
        approximate mass in grams and provide `estimated_weight_g` when
        the image/context supports an estimate.
    -   Clearly label this as an AI estimate, not a measurement.
        Estimate item weights independently; do not distribute a plate
        total evenly among items without evidence.
    -   Otherwise set `estimated_weight_g` to `null`, provide a
        qualitative serving description if useful, and ask the user to
        confirm.
    -   Do not imply that a single image can reliably determine mass,
        oil, sauce, hidden ingredients, or recipe.
4.  **Assess uncertainty**
    -   Assign a confidence from `0.0` to `1.0` to each food
        identification. This is a model-reported confidence indicator,
        not a calibrated probability unless independently calibrated.
    -   Use `low`, `medium`, or `high` uncertainty labels. A
        high-confidence food name does not imply a high-confidence
        weight.
    -   Record specific ambiguities in `needs_confirmation`.
5.  **Recognize possible source identity**
    -   If visible text/logo or user context suggests a brand, packaged
        product, or restaurant menu item, record it as a `candidate`
        with evidence.
    -   Do not claim the identity is verified. Never invent a URL.
6.  **Apply user edits when provided**
    -   Interpret `edit_request` against `existing_composition`.
    -   Preserve unchanged items and stable item IDs.
    -   Make only requested edits. If the text is ambiguous
        (e.g. "多一點"), ask a clarifying question or mark the affected
        value as needing confirmation.
    -   Mark changed fields as `user_provided` and preserve the prior AI
        estimate in audit metadata if the application supports it.
7.  **Stop at the human confirmation gate**
    -   Return the proposed composition and
        `status: "needs_user_confirmation"` unless the app explicitly
        indicates that the user has confirmed it.
    -   Do not start source verification or report generation until the
        app sends a composition marked `user_confirmed`.

## Output contract

Return JSON conforming to `nutrition-workflow.schema.json` with: -
`stage: "composition"` - `meal_id` - `status` - `items[]` -
`needs_confirmation[]` - `source_candidates[]` when applicable -
`errors[]` when applicable

Each item should include: - stable `item_id` - `name` - optional
`preparation` - optional `estimated_weight_g` (number or null) -
optional `portion_description` - `ingredients` for visually supported
internal ingredients - `candidate_names` for plausible but unconfirmed
ingredients - `identification_confidence` (0--1) - `uncertainty` -
field-level `field_origins` where practical

## Error handling

-   `IMAGE_UNREADABLE`: ask the user to retake/select a clearer image.
-   `NO_MEAL_DETECTED`: ask for a meal photo.
-   `AMBIGUOUS_COMPONENT`: provide plausible candidates and ask the user
    to choose; do not silently select one.
-   `PORTION_UNCERTAIN`: keep weight null and ask the user to estimate,
    choose a portion, or accept an explicitly marked estimate.
-   `EDIT_AMBIGUOUS`: ask a targeted clarification; do not alter
    unrelated items.
-   `MODEL_OUTPUT_INVALID`: retry once with a constrained JSON
    instruction; if still invalid, return a recoverable error for the
    app to display.
-   `IMAGE_TOO_LARGE`: request app-side resizing/compression; never
    claim the image was analyzed if it was not.

Do not include raw chain-of-thought. Return concise evidence/uncertainty
summaries only.

## Acceptance tests

1.  A clear photo of rice, chicken, and vegetables returns separate
    plausible items and no fabricated source URL.
2.  A blurry image returns `needs_user_input`; it does not fabricate a
    meal.
3.  If weight cannot be reliably inferred, `estimated_weight_g` is null
    and `PORTION_UNCERTAIN` or a confirmation question is present.
4.  User says "雞腿是烤的，不是炸的": only preparation for the chicken
    item changes; rice and vegetables remain unchanged.
5.  The result is valid JSON and conforms to the shared schema.
6.  No nutrition totals are produced in this stage.
7.  A brand/restaurant guess is marked as a candidate, not verified
    identity.
